# GateFlow AI learning guide — implemented work to date

This guide deliberately describes only behavior that exists in the repository today. It is updated phase-by-phase; future topics are not implied to be implemented just because they appear in the long-term plan.

## GateFlow traffic data and features

**What:** A feature is a numeric summary an ML algorithm can compare. Here, a request-log row becomes a one-minute aggregate per tenant, client, and route.

**Why:** Individual HTTP events are noisy and the database intentionally stores metadata, not request bodies. Window features describe traffic patterns without sending raw requests to a model.

**Input/output:** `request_logs` fields currently available are tenant/client/route IDs, method, status, latency, blocked state, request ID, and creation time. `app/ml/features.py` groups rows by minute and emits count/rate/latency features. Tenant IDs and other identifiers are grouping metadata, never numeric model inputs.

**Limitations:** Empty minutes are omitted. There is no request path, IP, payload, or reason field to derive more detailed behaviors from.

## Dataset construction and labels

`python -m scripts.generate_training_data` creates deterministic controlled examples using a seeded random generator. Scenarios include normal traffic and seven defined anomaly patterns. Every synthetic row is marked synthetic and carries a scenario label. Historical rows can optionally be extracted for a single selected tenant, but are marked `HISTORICAL_UNLABELED` and never assumed to be normal or used in supervised evaluation.

The per-scenario deterministic split assigns three of four sample indices to `train` and one to `test`. Model fitting uses only synthetic `NORMAL` rows in `train`; evaluation uses all labeled synthetic `test` rows. The generated dataset is a teaching fixture and not representative production validation.

## Unsupervised anomaly detection

**Unsupervised learning** fits patterns without requiring a correct label for every training example. It fits GateFlow because real production anomaly labels are not currently available. Evaluation still uses controlled synthetic labels, kept separate from model fitting.

**Isolation Forest:** The model builds randomized trees that isolate unusual points in fewer splits. It is a lightweight baseline for tabular traffic features. A median imputer and standard scaler are persisted with the estimator; scaling is important for distance-based LOF and does not change Isolation Forest feature ordering.

**Local Outlier Factor (LOF):** LOF compares a point's local density to its neighbors. It is included as an alternative on exactly the same train/test partitions. LOF can be sensitive to neighborhood size and does not automatically generalize outside its training distribution; novelty mode is used for future windows.

The feature list/order is fixed in `app/ml/schema.py`. IDs, timestamp, scenario name, split, and labels are not model features. The model artifact and metadata record algorithm, version, training time, feature schema, training count/configuration, evaluation metrics, and artifact digest. Artifacts use joblib (pickle-based) and must be treated as trusted internal build artifacts; never load user uploads.

## Evaluation vocabulary

A **true positive (TP)** is a labeled synthetic anomaly flagged by the detector. A **true negative (TN)** is a labeled normal synthetic window not flagged. A **false positive (FP)** is a normal window flagged as anomalous. A **false negative (FN)** is an anomaly the detector missed.

- Precision = TP / (TP + FP): among alerts, how many were labeled anomalies?
- Recall = TP / (TP + FN): among labeled anomalies, how many were found?
- F1 is the harmonic mean of precision and recall.

The comparison also measures inference elapsed time. Metrics describe only the held-out synthetic examples generated by that exact seed/size; they are not production quality claims. Review `comparison.json` before any explicit candidate promotion.

### Recorded controlled run (seed 42, 20 samples per scenario)

This actual run generated 160 synthetic windows: 120 training-split windows and 40 held-out test windows (five per scenario). Because the detector is fit only on known-normal data, its training set contained the 15 `NORMAL` training windows. Measured held-out results:

| Model | TP | TN | FP | FN | Precision | Recall | F1 | Inference time |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Isolation Forest | 13 | 5 | 0 | 22 | 1.000 | 0.371 | 0.542 | 103.78 ms |
| Local Outlier Factor | 34 | 5 | 0 | 1 | 1.000 | 0.971 | 0.986 | 69.52 ms |

The exact recorded timing is one run and varies by environment. LOF is the current active candidate because it scored better on this generated evaluation and was explicitly promoted; it is not declared superior for real customer traffic. Only five normal windows were in this holdout, and scenario generation makes the labels highly separable. Real traffic may behave differently. The model must be reevaluated with operationally representative, reviewed labels before production use.

## Model score versus probability

The API score is `-decision_function`, so a larger value means more anomalous relative to that fitted detector. This score is model-dependent and **not a probability**; no calibration has been implemented.

## Traffic forecasting (chronological experiment)

The optional forecasting pipeline converts a single tenant's request logs into a continuous one-minute count series, filling missing minutes with zero only between the first and last observed records. It uses lagged counts, rolling means/standard deviations, and cyclic time-of-day/day-of-week encodings. Separate Random Forest regressors predict the counts at +5 and +15 minutes. Features at time $t$ only use observed counts up to $t$; labels are future counts. A chronological holdout is used, and training origins are purged so their longest +15-minute target cannot cross into the test interval.

The baseline is persistence: future count equals the current observed minute count. MAE and RMSE are reported for model and baseline. In one measured 21-day synthetic run (30,240 minutes; 6,042 chronological test windows), +5 MAE was 5.709 vs baseline 6.301, RMSE 7.243 vs 8.072; +15 MAE was 6.294 vs baseline 7.441, RMSE 7.999 vs 9.554. This shows a gain only on the controlled synthetic generator, not real GateFlow data. No forecast model was promoted or exposed through the API.

## Training, inference, and promotion

Training is an offline command: generate a dataset, run `python -m scripts.train_anomaly`, inspect the comparison report, then explicitly promote a trusted candidate with `python -m scripts.promote_model`. Training does not silently replace the active model. The internal inference endpoint extracts recent logs for the supplied tenant, creates windows, loads the configured active artifact, and returns prediction plus transparent signals. The Go gateway has not yet been wired to call this endpoint, so browser clients cannot call it through the supported app architecture.

## Not implemented yet

Forecasting, embeddings, vector search/pgvector, document ingestion, semantic retrieval, RAG, LLM providers, tool calling, assistant/incident analysis, AI dashboard, anomaly persistence, and fine-tuning are future phases. They must not be presented as current GateFlow features.
